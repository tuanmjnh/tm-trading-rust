# TM Hub Integration Map

> Audit date: 2026-11-17`<br>
> Hub source: `D:\Applications\tm-hub`<br>
> Target repository: `D:\Applications\tm-trading-rust`
> Authority: `docs/TM-TRADING-RUST-MASTER-ROADMAP.md`

## 1. Purpose and decision summary

TM Hub remains authoritative for human identity, application registration, sessions, RBAC, route catalogs, and shared configuration. TM Trading Rust owns its domain records, Agent registry, service instances, operations, provider metadata, notification preferences, and delivery history.

The target integration is deliberately smaller and stricter than the legacy satellite integration:

1. **Human sessions use Hub-issued JWTs.** Desktop authenticates with TM Hub and presents the Hub access token to the local Management API.
2. **The Management API verifies Hub tokens locally.** It uses cached JWKS for RS256 and supports the legacy HS256 path only as an explicitly configured compatibility mode.
3. **The Rust product uses a dedicated Hub application registration.** The legacy `tm-trading` registration is not reused because its current route/role seed contains execution-oriented routes and permissions that are outside the Rust product boundary.
4. **API capabilities are defined and enforced in Rust.** Hub roles must be seeded with the same canonical capability strings before those endpoints are exposed.
5. **A local Agent is not a human Hub user.** It uses a separate, revocable, per-installation machine credential with Agent-only scopes. It must not use a human JWT or the broad Hub App Secret.
6. **Only non-secret public configuration is read from Hub.** Secrets remain in the platform secret store and are referenced indirectly.

## 2. Ownership boundary

| Concern | Authority | Rust behavior |
|---|---|---|
| User identity | TM Hub | Read `sub`, profile claims, and Hub session state; never copy users locally |
| Human access/refresh tokens | TM Hub | Hold transiently and verify at the API boundary; never persist in MongoDB or UI state |
| Application registration | TM Hub | Use a dedicated Rust app ID from deployment configuration |
| Roles, permissions, capabilities | TM Hub | Define the Rust capability vocabulary, seed matching Hub roles, and enforce every protected endpoint |
| Route catalog | TM Hub | Read the pruned catalog for client navigation; do not use it as API authorization |
| Shared public configuration | TM Hub | Read from the public-config endpoint; cache with bounded freshness |
| Secret configuration | Platform secret store / OS credential store | Store only `secretRef` and metadata in configuration or MongoDB |
| Agent identity | TM Trading Management API/Agent registry | Register per installation/host; issue revocable Agent-only credential |
| Service/operation state | TM Trading Rust | Persist in MongoDB and expose through `/api/v1` |
| Domain/provider/notification data | TM Trading Rust | Own and persist independently from Hub |

TM Hub must not become a registry for worker processes, service instances, operation history, provider instances, AI model selections, or delivery records.

## 3. Application identity decision

### 3.1 Dedicated application

The target application is registered in TM Hub under the logical name `TM Trading Rust`. Its deployment-specific `appId` is read from configuration; it is never hardcoded in Rust source or committed to `.env`.

A dedicated registration is required because the current legacy `tm-trading` seed contains routes for orders, paper trading, positions, accounts, bots, and autonomous research agents. Reusing that registration would either expose those surfaces to the Rust client or require destructive edits to a live legacy registration.

The Hub seed for the Rust application must contain only:

- the Dashboard and Control Center route entries;
- route labels/icons needed by the client;
- read-only domain navigation entries that already have a Rust API contract;
- no order, paper, position, account, bot, execution, or autonomous-agent route.

The application ID currently visible in legacy examples is not accepted as the Rust app ID. The seed process resolves a Hub application ID dynamically, and reset seeds generate a new suffix.

### 3.2 Required Hub-side registration fields

| Field | Requirement |
|---|---|
| Logical name | `TM Trading Rust` |
| Application ID | Generated by Hub seed/registration and injected into target deployment configuration |
| Active state | Active only in environments where the Rust application is deployed |
| Allowed origins | Local native client needs no browser origin; add the future Web origin only when deployed |
| Description | Information-first market intelligence and service management |
| Human role assignments | Users who may access the Rust application receive a Rust app role |

## 4. Endpoint contract

The paths below are observed in the Hub source. Their live availability in the selected deployment was not verified.

| Method and path | Authentication | Rust use | Decision |
|---|---|---|---|
| `POST /api/v1/auth/login` | Public, rate-limited | Human password login | Use from Desktop |
| `POST /api/v1/auth/totp/login` | Pending TOTP challenge | Complete MFA | Use when login returns `totpRequired` |
| `POST /api/v1/auth/refresh` | Public with refresh token | Rotate an expired access token | Use; persist only in the OS credential store |
| `POST /api/v1/auth/introspect` | Bearer access token | Diagnostic token validation | Do not call per request; optional diagnostic only |
| `GET /api/v1/auth/jwks` | Public | Obtain Hub RS256 verification keys | Use with bounded cache and key-ID refresh |
| `GET /api/v1/auth/permissions` | Bearer access token | Read effective permissions | Optional diagnostic/session refresh; API enforcement uses verified claims |
| `GET /api/v1/auth/routes` | Bearer access token | Read the user-pruned route tree | Use for Desktop/Web navigation |
| `GET /api/v1/auth/me` | Bearer access token | Read current profile/feature information | Optional UI profile refresh |
| `POST /api/v1/auth/logout` | Public with refresh token | Revoke the refresh session | Use on explicit sign-out |
| `GET /api/v1/apps/:id/routes` | Human JWT + app access + `routes.read` | Read the complete application route catalog | Not required for normal client navigation; administrative use only |
| `GET /api/v1/configs/public` | Public with `X-App-Id` or `appId` | Read shared non-secret public configuration | Use with the Rust app ID |

### 4.1 Request conventions

- Hub requests identify the application with `X-App-Id` where the endpoint supports it and with the `appId` request field for login/refresh.
- Desktop sends a stable per-installation `deviceId` and `platform: "desktop"` so Hub device limits and session replacement behave consistently.
- Rust never sends the Hub App Secret from a distributed Desktop binary.
- The legacy `@tuanmjnh/tm-hub-client` browser-oriented wrapper is not reused in Rust. The small auth/config client is implemented against these HTTP contracts.

## 5. Human authentication flow

### 5.1 Password login

```text
Desktop
  -> POST Hub /auth/login
     { appId, email, password, platform, deviceId }
  -> Hub validates credentials and device policy
  -> either access/refresh session response
     or { totpRequired: true, pendingTotpToken }
```

On success, the Hub response contains:

```text
accessToken
refreshToken
expiresIn
user { id, email, name, username, avatarUrl, appId, roles, permissions, allowedRoutes }
```

The current source reports an access-token lifetime of 900 seconds and a refresh-token lifetime of seven days. Runtime values remain authoritative; the Rust client must use `expiresIn` rather than assuming those values.

### 5.2 TOTP completion

When `totpRequired` is true, Desktop submits `pendingTotpToken` and the user-entered `code` to `POST /api/v1/auth/totp/login`. The pending token is a five-minute challenge, not an access token.

Desktop must not implement TOTP generation itself. The human enters or approves the code through the supported UI flow. Rate-limit responses include `Retry-After` and must be presented without automatic credential retry loops.

### 5.3 Refresh rotation

`POST /api/v1/auth/refresh` requires the current refresh token and Rust app ID. Hub atomically marks the old token used and returns a new access/refresh pair.

Rust behavior:

- serialize refresh attempts per session so two requests cannot race on one refresh token;
- treat reuse detection as a session compromise signal: stop refreshing, clear the local session, and require sign-in;
- never retry an invalid or reused refresh token automatically;
- keep the new refresh token only in Windows Credential Manager (or the approved platform secret store), not in browser storage, MongoDB, logs, or diagnostics.

### 5.4 Sign-out

Desktop calls `POST /api/v1/auth/logout` with the refresh token when available, then clears the local Hub session and API bootstrap credential where appropriate. Local API process state is not terminated by sign-out.

## 6. Token verification contract

### 6.1 Current Hub token shape

The verified Hub access token currently contains:

```text
sub            user ID
appId          application ID
email          email address
name           display name
roles          role IDs
permissions    effective capability strings
allowedRoutes  route IDs or ["*"]
iat / exp      standard JWT timestamps
```

The current token does not define a separate issuer, audience, token type, or explicit scope claim. Therefore Rust verifies signature, expiry, expected `appId`, and required claim types. Hub-side addition of `iss` and `aud` is recommended before cloud multi-tenant exposure; until then, the Rust app ID is the application boundary.

### 6.2 Verification algorithm

1. Parse and validate the compact JWS structure.
2. Reject an algorithm outside the configured allow-list.
3. For `RS256`, select a trusted JWKS key by `kid`; fetch JWKS on cache miss and retain previous keys during a bounded rotation overlap.
4. For `HS256`, use an explicitly injected legacy shared secret only in a named compatibility mode.
5. Never allow the token header to choose an arbitrary algorithm or key family.
6. Validate `exp`, `iat`, `sub`, and `appId`; require a non-empty `sub` and the configured Rust app ID.
7. Validate that `roles`, `permissions`, and `allowedRoutes` are arrays of strings when present.
8. Treat malformed claims as an authentication failure rather than silently dropping the claim.

Production configuration fails closed when no compatible verifier is available. A missing shared secret must not silently enable HS256.

### 6.3 RS256 and HS256 compatibility

| Mode | Use | Status |
|---|---|---|
| RS256 + Hub JWKS | Target default | Required before production readiness |
| HS256 + explicit shared secret | Existing single-node Hub compatibility only | Temporary, documented, and disabled by default in production |
| Introspection per request | Fallback/diagnostic only | Not the normal API path |

### 6.4 Token handling rules

- Access tokens live in process memory for the active request/session.
- Refresh tokens live in Windows Credential Manager or the approved cloud secret store.
- Authorization headers, refresh tokens, device secrets, and app secrets are redacted from tracing and diagnostic output.
- The Management API does not log the full token or decoded claims.
- The API returns `401` for a missing, invalid, expired, wrong-app, or wrong-audience token.

## 7. Authorization and capability mapping

### 7.1 Canonical Rust capabilities

The roadmap names the target capability vocabulary. It is authoritative for API enforcement:

```text
trading.dashboard.read
trading.market.read
trading.research.read
trading.watchlists.manage
trading.providers.read
trading.providers.manage
trading.ai_models.manage
trading.services.read
trading.services.control
trading.agents.manage
trading.notifications.manage
trading.diagnostics.read
trading.settings.manage
```

### 7.2 Hub representation gap

The current Hub capability catalog does not contain these `trading.*` values. Hub role permissions use `{ module, actions }`, and the Hub converts them to `module.action` strings. A role entry of `module: "trading", actions: ["read"]` becomes `trading.read`, not `trading.services.read`.

Before protected Rust endpoints are enabled, TM Hub must:

1. register the canonical Rust capabilities in its system capability catalog;
2. accept the `trading` module with actions such as `services.read`, `services.control`, and `agents.manage`;
3. seed read-only, operator, and administrator roles with those capabilities;
4. assign users to those roles for the Rust application; and
5. include the capabilities in issued JWT `permissions` claims.

The Rust API must not assume that a generic existing Hub permission implies a Rust capability. Enforcement uses exact capability matching, with `*` reserved for Hub root/full-access identities.

### 7.3 Proposed role mapping

| Rust role | Capabilities | Intended use |
|---|---|---|
| Viewer | `trading.dashboard.read`, `trading.market.read`, `trading.research.read`, `trading.services.read` | Read-only product access |
| Operator | Viewer plus `trading.watchlists.manage`, `trading.notifications.manage` | Manage user-owned research preferences and notifications |
| Service Operator | Viewer plus `trading.services.control`, `trading.agents.manage` | Start/stop/restart registered services and Agents |
| Settings Operator | Viewer plus `trading.providers.read`, `trading.providers.manage`, `trading.ai_models.manage`, `trading.settings.manage` | Configure provider/model/settings metadata |
| Administrator | All Rust capabilities plus diagnostics | Administer the Rust application |

No role grants order, paper, position, account, bot, or autonomous-execution capability.

### 7.4 Enforcement rules

- Every protected endpoint declares one required capability or an explicit “any of” set.
- Route visibility and `allowedRoutes` never substitute for endpoint authorization.
- The API derives owner scope from the verified Hub `sub`; it does not accept an owner ID from the request body.
- A user may operate only a service/Agent visible to that user according to the target owner/assignment policy.
- Capability checks occur in the Management API, not only in Desktop.
- Hub-root wildcard access is accepted only when the token belongs to the expected Rust app and is otherwise valid.

## 8. Route catalog integration

### 8.1 Client navigation

Desktop/Web use `GET /api/v1/auth/routes` with the access token and the Rust app ID. Hub returns a route tree pruned by role capabilities and `allowedRoutes`.

Rust behavior:

- treat the Hub route tree as navigation metadata only;
- map stable Hub route IDs to localized Desktop surfaces in the client layer;
- do not derive API authorization from the tree;
- tolerate an unknown route label by using a safe fallback rather than failing the whole client;
- refresh the catalog after login, permission change, or explicit retry.

### 8.2 Seed cleanup requirement

The current legacy Trading seed includes hidden or routable entries for trading, paper, orders, positions, accounts, bots, autonomous agents, and execution-oriented research. The Rust application seed must not copy those entries.

The Rust application should expose only stable navigation for:

- Dashboard;
- Control Center / Services;
- Agents (when the corresponding API exists);
- market/research/news information surfaces that have a Rust API;
- settings surfaces that have a Rust API.

## 9. Shared configuration integration

### 9.1 Public configuration

`GET /api/v1/configs/public` accepts `X-App-Id` or `appId` and returns only rows where both `is_public = true` and `is_secret = false`.

Rust may read non-secret shared values such as:

- enabled feature flags;
- locale/timezone defaults;
- public product branding;
- public provider catalog metadata that Hub owns.

### 9.2 Configuration precedence

The roadmap precedence remains authoritative:

1. process/deployment secret injection;
2. OS secure secret store referenced by `secretRef`;
3. user-managed non-secret application configuration;
4. Hub public configuration;
5. built-in safe defaults.

Hub public configuration cannot override a missing required production secret or change a security-sensitive local binding.

### 9.3 Secret exclusion

The Rust client must never request, cache, or display secret Hub rows. Existing Hub storage/AI relay secret flows are separate from the Trading Management API and are not part of the first slice.

## 10. Agent and machine authentication

### 10.1 Why existing Hub identities are insufficient

The Hub currently supports:

- human JWT access/refresh tokens;
- `X-App-Id` + `X-App-Secret` server-to-server application authentication;
- enrolled device credentials with the limited scopes `ai.relay` and `storage.user`.

None is an appropriate Agent identity for this product:

- a human JWT violates the machine-identity boundary;
- the App Secret is app-wide, has no per-host revocation, and is too broad;
- current device scopes do not cover Agent registration, heartbeat, or command claims.

### 10.2 Target Agent identity

The Management API owns an Agent registry with one identity per installation/host. An Agent receives a dedicated credential bound to:

```text
agentId
installationId
credentialId
scopes
issuedAt
expiresAt
revokedAt
```

Minimum scopes:

```text
agent.register
agent.heartbeat
agent.commands.claim
agent.commands.report
agent.snapshot.write
```

The Agent credential cannot invoke human/user endpoints. A user command is authorized by the Management API before it enters the durable operation queue. The Agent revalidates command target, expiry, action allow-list, and fencing token before execution.

### 10.3 Local mode

- The local Management API binds to `127.0.0.1` only.
- A per-install local bootstrap credential is generated once and stored through Windows Credential Manager.
- The local Agent is paired through that bootstrap credential or an explicit local approval step.
- The API issues a distinct Agent-only credential; the bootstrap credential is not reused for every Agent request.
- Revoking an Agent prevents new command claims immediately and is visible in the Agent registry.

### 10.4 Cloud mode

Cloud registration is deferred to the roadmap's remote-Agent phase. It must use an approved registration/pairing flow and a TLS-protected, per-Agent, revocable credential. The Agent connects outbound and never requires inbound access to the user's PC.

## 11. Failure behavior

| Failure | Required behavior |
|---|---|
| Hub unavailable at startup | The API may start only if configured Hub keys are already cached and valid; otherwise protected endpoints fail closed |
| JWKS fetch unavailable | Use a valid cached key during its bounded lifetime; do not accept an unknown key |
| Hub key rotated | Fetch by new `kid`, retain the prior key for the bounded overlap, refresh cache |
| Access token expired | Return `401`; Desktop refreshes once, then retries the original request at most once |
| Refresh token invalid/reused | Clear the session and require sign-in; never loop |
| Wrong app ID in token | Return `401`; do not disclose cross-app role details |
| Missing capability | Return `403` with the required capability code in a redacted error body |
| Hub route/config unavailable | Product read endpoints may remain available if their data is local; protected actions still fail closed |
| Agent credential revoked | Stop new claims, report the revocation, and preserve operation history |

## 12. Error and correlation requirements

The Hub uses `{ success, data }` success envelopes and error status messages such as `error.unauthorized`, `error.forbidden`, and `error.tokenMissing`. The Rust Management API keeps its own stable `/api/v1` error contract and does not expose raw Hub error bodies.

Every authenticated Rust request records, without token values:

```text
correlationId
operationId (when applicable)
hub subject
hub app ID
required capability
result status
```

The UI displays a generic authentication or authorization message and may show a stable Hub error code only after it is mapped into the Rust localization/error layer.

## 13. Implementation sequence

1. **Hub preparation**
   - register the dedicated Rust application;
   - add the canonical Rust capabilities to the Hub catalog;
   - seed read-only/operator roles and Rust routes;
   - configure RS256 and expose non-empty JWKS;
   - verify refresh/TOTP/device behavior against a test account.

2. **Rust auth client and verifier**
   - implement login, TOTP completion, refresh rotation, logout, and JWKS retrieval;
   - implement strict token verification and capability extraction;
   - store refresh tokens through the secret-store abstraction;
   - test expiry, wrong app, wrong algorithm, unknown key, rotation, and refresh reuse.

3. **Rust API authorization**
   - define exact capability guards;
   - derive owner scope from `sub`;
   - add permission and tenancy tests before enabling protected routes.

4. **Agent identity**
   - implement the Agent registry and local pairing/bootstrap;
   - issue and rotate Agent-only credentials;
   - enforce scopes, target, expiry, lease, and fencing on every command.

## 14. Live verification plan

No live Hub call was made during this audit. The following checks remain required before declaring the integration complete:

| Verification | Result | Required evidence |
|---|---|---|
| Rust app exists, is active, and has the expected ID | BLOCKED | Sanitized Hub app record/lookup |
| Human password login succeeds without MFA | BLOCKED | Test-account response with tokens redacted |
| TOTP challenge/completion succeeds | BLOCKED | Test-account response with challenge/code redacted |
| Refresh rotates exactly once | BLOCKED | Before/after token fingerprints only; no raw token |
| Refresh reuse is rejected | BLOCKED | Test response and local-session behavior |
| Deployed signing mode is RS256 | BLOCKED | Token header and non-empty JWKS; no token value logged |
| JWKS rotation works | BLOCKED | Sanitized old/new `kid` behavior |
| Rust capabilities appear in JWT and Hub role editor | BLOCKED | Permission list with subject details redacted |
| User route tree excludes execution surfaces | BLOCKED | Sanitized route-ID list |
| Public config excludes secret rows | BLOCKED | Key list and secret-presence assertions only |
| Agent registration/credential lifecycle | BLOCKED | Requires a Hub or Management API Agent-scope implementation |

Commands must be run against a dedicated test application/account and must not print access tokens, refresh tokens, pending TOTP challenges, App Secrets, device secrets, or database credentials.

## 15. Phase 0 conclusion

The Hub source provides sufficient contracts for human login, TOTP, refresh rotation, JWKS verification, permission inspection, pruned route retrieval, and public configuration. The integration has two material gaps that must be resolved before protected Rust endpoints are enabled:

1. the Hub capability catalog and Rust application seed do not yet contain the canonical `trading.*` capabilities and Rust-only routes;
2. no dedicated per-host Agent registration/token scope exists.

The safe first implementation is therefore to build the Rust verifier and API authorization against exact capabilities, keep the local Agent on a separate Trading-owned credential, and leave live integration marked `BLOCKED` until the Hub-side preparation and live checks above pass.
